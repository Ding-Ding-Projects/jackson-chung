# Local browser tools

The `tools` feature is a browser-local workspace shared by the website and desktop renderer. It does not require the native companion or a network request.

## Converter

`pdf-lib` 1.17.1 provides inspect, split, merge, extract, reorder, rotation and title metadata operations. Generated documents reopen before download and page geometry, rotation and metadata are checked. Copy operations preserve selected order. Original file bytes are never written. Inputs are limited to 20 MiB total, 20 files and 500 pages. A dedicated module worker is terminated on cancellation or a 30-second deadline. Outputs are downloaded only after validation.

Interactive form and encrypted PDF sources are rejected. PDF signature dictionaries are detected and rejected. Other opaque PDF features are unsupported. Copy operations do not promise preservation of annotations, attachments, outlines, document metadata or accessibility structure. Do not use these operations for signed or archival documents. Content-level page-order validation and exhaustive opaque-feature handling remain pending.

JSON row arrays, CSV and TSV support quoted fields, embedded delimiters and newlines. Base64 and hexadecimal encode/decode exact bytes. ZIP creation uses bundled `fflate` 0.8.2 and reparses its output. ZIP extraction is disabled until bounded decompression has been implemented. PNG/JPEG inputs can be encoded to PNG, JPEG or WebP through isolated worker canvas when the browser supports it. Header inspection limits dimensions before decode to 8192 pixels per side and 16 megapixels and rejects animated PNG. Outputs are reopened and dimension-checked. Metadata is removed; JPEG/WebP are lossy and JPEG fills transparency white. Office spreadsheet adapters and source-language compilation remain unavailable.

## Audio and video

The bounded media backend uses the pinned single-thread `@ffmpeg/core` 0.12.10 UMD core directly inside one dedicated classic worker. It does not spawn nested workers or require SharedArrayBuffer. The wrapper package's module-worker route cannot import this UMD core as an ESM default; the classic worker uses `importScripts` and the core's source-exposed worker API instead. The required local asset copies, expected package hashes and MIME types are in [media-assets.json](media-assets.json). Root build/package integration must copy all four files. URLs resolve from Vite's base URL and the current document, preserving a hosted subpath and the desktop custom origin. No CDN URL or upload is used. Missing assets or incompatible browser APIs cause failure, never a network fallback.

**Public binary distribution is pending its license/source boundary.** The installed core declares GPL-2.0-or-later but its npm package contains only `dist` and package metadata. The [official release for tag v12.15](https://github.com/ffmpegwasm/ffmpeg.wasm/releases/tag/v12.15) identifies core 0.12.10; tag v0.12.10 instead identifies an older core. The v12.15 build ref is `71aa99d37c02a7b4c435275ca9ef50e612f6efa1`. Its Dockerfile uses Emscripten 3.1.40, FFmpeg n5.1.4, `--enable-gpl`, project bindings and build scripts, and linked codec/font components with individual licenses. The LAME source is a floating `master` reference, so the package does not by itself prove the exact build-source revisions. Applicable notices and complete corresponding source/build provenance must be resolved before distributing the WASM. The [official FAQ](https://ffmpegwasm.netlify.app/docs/faq/) confirms that core licensing follows FFmpeg and its linked components; the wrapper's MIT license does not replace those licenses. No distribution-ready claim is made here.

### Availability discovery

Media category buttons, target choices, direct execution and queue intake remain disabled unless local availability discovery succeeds. The current deployment without verified distribution proof therefore exposes a pending reason and keeps text tools actionable. Discovery first requests `vendor/ffmpeg/distribution.json` from the same document base. Missing or unapproved proof stops before fetching WASM or probing codecs. No CDN or alternate origin is attempted. Fetches have an abort deadline and bounded response sizes.

The future root-owned distribution manifest must contain `version: 1`, `coreVersion: "0.12.10"`, `licenseAndSourceVerified: true`, a safe local `.txt` `noticeFile`, and exactly four `files` records. Each record has an exact `name` (`ffmpeg-core.js`, `ffmpeg-core.wasm`, `media-worker.js`, `media-plan.mjs`), integer `bytes` and lowercase SHA-256 `sha256`. Do not produce the approval flag until the corresponding-source and notice boundary is actually resolved. The browser trusts this maintainer-authored attestation; it does not independently decide legal compliance.

After reading the local notice, discovery fetches and hashes each bounded asset, then starts a temporary dedicated worker to run the core's actual encoder listing. Required encoder names are checked per target: PCM, LAME, Vorbis, FLAC, H.264/AAC and VP8/Vorbis respectively. Absent encoders disable their dependent targets with a visible reason. Hash mismatch, unavailable assets, browser limitations or codec-probe failure keep media disabled. Discovery is cached for the current page lifetime; reload after replacing the verified distribution. The temporary worker terminates after discovery or its deadline. These checks establish local availability, not completed conversion or packaged-runtime acceptance.

Audio outputs are WAV PCM, MP3, OGG Vorbis and FLAC. Video outputs are H.264/AAC MP4 and VP8/Vorbis WebM. Signature-accepted sources are WAV, MP3, OGG, FLAC, MP4 and WebM, subject to actual FFprobe decoding. Audio extraction uses the first audio stream and discards video. Video transcodes use the first video and optional first audio stream. Guided start/duration controls implement decoded trimming. No arbitrary arguments, filenames, paths, codecs or remux operation are accepted. Virtual filesystem names are generated from the allowlisted detected container. Protocol access is restricted to the worker's virtual files.

Each source is at most 20 MiB. Audio duration is at most 600 seconds. Video is at most 60 seconds, 1920 by 1080 and 60 fps; video output is at most 1280 by 720 at 24 fps. At most four input streams and eight source audio channels are accepted. Output audio normalizes to stereo 44.1 kHz. MP3/OGG/video outputs are lossy; metadata, chapters and extra streams are removed. FLAC/WAV preserve the normalized audio, not original sample-rate/channel metadata. Probe deadlines are five seconds, encode deadline 30 seconds, with a 30-second outer worker lifetime. Cancellation, pause and disconnect terminate the sole worker. The browser does not expose a hard per-worker memory quota; limits constrain accepted bytes, geometry, duration and execution, and resource exhaustion remains a failure. No stronger memory-isolation claim is made.

FFmpeg output timestamp events report actual processed seconds; they are not labeled CPU completion percentages. Both direct conversion and the durable queue select this backend. The queue still reads one source per job and has no total-file cap. Before delivery, output size, container signature, stream structure, duration and video dimensions are validated by reopening with FFprobe. A file at the output size cap or with truncated duration is rejected. Originals stay untouched. Actual WASM execution, codec availability and packaged offline operation remain pending browser acceptance; pure planner checks are not runtime evidence.

## Code and text

Guided operations format or compact JSON, normalize LF/CRLF line endings, encode UTF-8 with BOM or UTF-16LE, decode BOM-marked UTF-16LE to UTF-8, and escape HTML characters into plain text. They never execute source code. Input/output is bounded to 2 MiB, invalid encodings and NUL-bearing binary content are rejected, JSON nesting is bounded to 64 levels and comma/item count to 100,000. Output is decoded or parsed again before delivery. JSON formatting follows JavaScript JSON.parse semantics, including numeric normalization and last-value behavior for duplicate keys. These transformations are disclosed; source bytes remain unchanged. General compilers and AST rewrites remain unavailable.

Each of the eight categories has independent literal search and an adjacent regex builder with editable expressions, flags, character classes, groups, lookarounds, quantifiers, Unicode properties, backreferences and a test example. Regex matching executes in a disposable worker with a 150 ms deadline. Unsupported adapters remain visible with their missing capability. A complete visual regex graph and image preview remain unfinished. Control labels and capability explanations use the English/Cantonese translation callback; exact adapter and format identifiers remain literal. No offline packaged-runtime or browser interaction acceptance is claimed.

## Durable queue

The queue has no fixed total-file cap. Each source is bounded to 20 MiB and stored separately in IndexedDB. Intake reads one selected file at a time, applies estimated storage-capacity preflight and stops honestly on unavailable quota information or storage failure. A job is processed by one worker at a time; only one bounded source enters memory. A Web Lock prevents simultaneous processors across tabs. Browsers without Web Locks cannot process the durable queue. Metadata reads and rendering are paged, 20 rows at a time, with a maximum page request of 50. Job records contain no source contents or paths.

Pause is durable and terminates current processing, preserving its original source for restart. Running jobs interrupted by reload recover to queued state, with at most three automatic attempts. Cancellation removes saved source bytes and late outputs cannot resurrect canceled records. Completed outputs stay local until downloaded or removed. Removal deletes both metadata and saved bytes. Browser eviction remains possible, so this is not a backup. Progress reports completed phases rather than an invented CPU completion percentage. Direct conversion retains its bounded transient batch; durable intake is the route for an arbitrarily long workload. Queue PDF merge currently handles one source per job; direct merge accepts several bounded sources. Multi-source persistent merge, queue bulk selection and portable result-manifest export remain unfinished.

## Authenticator

RFC 6238 codes use browser WebCrypto HMAC SHA-1, SHA-256 or SHA-512, six to eight digits and periods from 1 to 86,400 seconds. The default is SHA-1, six digits, 30 seconds. Tests cover all published eight-digit vectors and six-digit suffixes.

Entries are stored in an AES-GCM encrypted local browser-storage vault. A password derives the encryption key using PBKDF2 SHA-256 with 310,000 iterations and a fresh 16-byte salt for each save. Every save uses a fresh 12-byte IV. Plaintext entries remain in memory while unlocked and are cleared when locked or disconnected. Stored secrets have no display or export path. The registration input accepts only new user-supplied material and clears after successful storage.

All vault creation and mutations use one local promise queue and an exclusive origin-wide Web Lock. Each mutation rereads and decrypts the latest stored ciphertext while holding that lock, then computes its change, so concurrent add/remove operations and other cooperating tabs retain each other's records. A final ciphertext revision comparison rejects writers outside the protocol instead of overwriting their newer data. Locking invalidates active and queued operations through a generation check before every write, including initial creation. Browsers without Web Locks cannot create or write this vault; no unsafe fallback is attempted.

New registration generates a local random secret and renders a genuine QR using bundled `qrcode` 1.5.4. The manual secret is visible only during new registration, alongside its algorithm, digits and period. Confirmation accepts a current RFC code within one adjacent period and rejects wrong codes before submitting the entry to the encrypted vault. Manual `otpauth://totp` import validates supported parameters and duplicate fields. Camera import uses browser permission, bounded 640 by 480 frames and a worker with bundled `jsqr` 1.4.0, stopping after 30 seconds. Frames and registration material are not persisted, logged or exported. Camera tracks stop on disconnect or explicit stop.

This is local convenience protection, not server authentication. Same-origin scripts can access an unlocked vault. Browser storage can be evicted or cleared. Resetting a lost vault requires clearing this origin's browser storage and permanently loses its entries. No remote backup exists. Account search reuses the independent literal/regex builder and filters visible records without searching secrets. Grouping, reorder, bulk actions, protected mutation history and native credential-vault integration remain unfinished. Clipboard writes require browser permission. Successful decryption of an existing vault calls the optional shared store `setLocalAuthenticated(true)` through a local dynamic module import; locking calls `false`. A generation counter prevents a delayed import from restoring authentication after locking. No dispatchable DOM authentication event exists. Creating a new empty vault does not establish this authentication state.

## Verification

Run `node --test tests/tools*.test.mjs` for synthetic RFC vectors, vault tamper and wrong-password rejection, supported PDF operations, source-byte preservation, table round trips, encoding round trips, malformed sources and byte bounds. Queue tests use `fake-indexeddb` 6.2.4 and cover 75 queued files, page bounds, crash recovery, retry limits, persisted pause, cancellation/late output, cross-tab removal without orphan output and storage preflight. Vault concurrency tests use real encryption and independently controlled interleavings to verify concurrent add/remove preservation, lock during encryption, queued-write invalidation, revision conflicts and creation cancellation. Genuine generated QR matrices are independently decoded by `jsqr`, and parameters round-trip through the URI parser. Pairing tests reject wrong codes and enforce bounded skew. These source-level checks do not establish installed-runtime, camera, screen-reader or responsive-layout acceptance.
